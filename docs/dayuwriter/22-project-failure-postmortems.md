# DayuWriter 项目失败复盘与防复发记录

## 目的与记法

本文记录本项目中已经发生、影响了结论、进度或真实硬件安全的失败。它不同于 [18-工程经验与教训](18-engineering-lessons.md)：后者提炼通用原则；本文只写本项目的实际事件。

每条记录分为四种证据强度：

- **已证实根因**：有设备输出、代码路径、现场复现或修复后的对照证据。
- **部分证实**：现象和排除项明确，但唯一根因未被直接测得。
- **未证实**：只保留现象，明确不把推测当结论。
- **防复发措施**：后续代码、流程或检查表中应执行的动作。

本文不以“最终成功”掩盖失败；同一问题可能在不同电脑、相机姿态或供电状态下再次出现。

## 1. GRBL 返回 `ok`，但电机完全不动

| 项目 | 记录 |
| --- | --- |
| 时间 | 2026-07-26 恢复阶段 |
| 现象 | 上位机和 GRBL 都能响应，`MPos` 会变化，但 XYZ 电机无声音、无位移。 |
| 已证实根因 | 12 V 电机供电没有可靠接入 CNC V3 的 `12-36V` 端子。Arduino UNO 圆形电源孔不能向 A4988 电机驱动链路供电；压紧 CNC V3 端子后电机声音和运动恢复。 |
| 错误认识 | 把串口层的 `ok` 误当作“整机已经动作”。 |
| 修复 | 红线接 `+`、黑线接 `-` 到 CNC V3 `12-36V`；接电后先做小幅单轴实测。 |
| 防复发 | 每次出现“`ok` 但不动”，先检查 12 V 端子、适配器和驱动供电，再考虑刷固件或修改步距。每次真机动作必须同时记录 `ok`、最终 `Idle` 和肉眼观察。 |

这条问题说明通信链路与功率链路是独立的：前者正常不能推出后者正常。

## 2. 历史端口、固件和脚本被误当成当前配置

| 项目 | 记录 |
| --- | --- |
| 时间 | 恢复初期 |
| 现象 | 历史对话给出 `COM11`、GRBL 1.1h 与旧脚本；现场枚举实际为 CH340，端口曾为 `COM3`，后续 USB 变化为 `COM4`，启动信息为 GRBL 1.1f。 |
| 已证实根因 | Windows COM 编号由当前电脑/USB 插口/驱动决定；历史文本不是设备实时身份。旧脚本含硬编码端口，部分还会发送 `G92`、写参数或无限等待。 |
| 修复 | 使用设备管理器和只读 GRBL 查询重新建立基线；首次控制入口改为有边界的 Python 模块。 |
| 防复发 | 任何电脑、USB 重插或演示前，都先查 `USB-SERIAL CH340 (COMx)`；把 `COMx` 写在运行参数中，不写死到控制代码。旧脚本只能审计，不能直接接真机运行。 |

## 3. 将 MPos 或串口会话误解为物理绝对位置

| 项目 | 记录 |
| --- | --- |
| 现象 | 串口重连、12 V 断电、手推笔架或疑似丢步后，软件仍能给出 MPos。 |
| 已证实事实 | 当前机构没有已验证的自动回零、编码器闭环或可作为绝对位置依据的限位链路。MPos 是 GRBL 的开环内部状态。 |
| 风险 | 在错误的物理位置继续按“回 P0”或视觉目标运行，可能造成碰撞或坐标整体偏移。 |
| 修复 | 建立人工物理 P0：在每次失效事件后，将笔尖实际对准纸面 P0 才重新解释坐标。 |
| 防复发 | 将“断电、USB 重插、复位、手推、碰撞、丢步疑虑”列为机械 P0 失效事件。代码不把 `MPos=0` 表述为“已经物理到 P0”。 |

## 4. `Pn:P` 持续有效，却没有完成探针根因排查

| 项目 | 记录 |
| --- | --- |
| 现象 | 多次 GRBL 状态帧包含 `Pn:P`。 |
| 已证实事实 | GRBL 将 `P` 报告为探针输入有效。 |
| 未证实部分 | 该输入究竟来自悬空线、接线极性、扩展板状态还是其他硬件原因，尚未通过电路测量或逐线排查确定。 |
| 当前限制 | 不进行基于探针的 Z 标定、自动触纸或无人值守 Z 动作。 |
| 防复发 | 在使用探针前，断电检查探针端子和线束，通电后以状态帧确认空闲/触发状态；只有行为与接线一致时才进入探针测试。 |

这是一个未闭环问题，不能因为当前红方块演示能运行就被遗忘。

## 5. 新电脑环境被中断后看似“已创建”，实际缺少依赖

| 项目 | 记录 |
| --- | --- |
| 现象 | `conda env create` 在 pip 依赖阶段长时间运行后被中断；随后环境可激活，但 `import numpy` 失败。 |
| 已证实根因 | 环境目录已创建不代表 pip 依赖阶段已完成；当时 `numpy` 未安装。 |
| 修复 | 在激活的 `dayuwriter-control` 中用 `python -m pip install --only-binary=:all:` 单独安装并随后导入验证。 |
| 防复发 | 环境创建后必须运行一次 `import serial, numpy, pyrealsense2, cv2` 检查，不能只看 `conda env list`。同一环境不要在两个终端并行安装。 |

环境是否可用以解释器实际导入为准，不以目录、提示符或安装进度条为准。

## 6. Tkinter 测试在收集阶段被 Windows 策略阻断

| 项目 | 记录 |
| --- | --- |
| 时间 | 2026-07-28 |
| 现象 | 全量 pytest 在导入 `_tkinter` 时出现 `DLL load failed ... Application control policy blocked this file`。 |
| 已证实根因 | Windows 应用控制策略阻止当前环境加载标准库 `_tkinter` DLL；失败发生在测试收集、平面标定模块导入之前。 |
| 排除项 | 这不是新平面映射代码的回归证据，也不是串口或相机故障。 |
| 修复/绕过 | 先运行不依赖 GUI 的测试；需要监视器 GUI 时，恢复系统策略许可或使用允许加载 Tkinter 的 Python 环境。 |
| 防复发 | CI/离线算法测试与 GUI 依赖分开；报告中明确说明“测试未执行”还是“代码测试失败”。 |

## 7. D435i 中心像素深度为零，被误判为相机不可用

| 项目 | 记录 |
| --- | --- |
| 时间 | 2026-07-27 |
| 现象 | `camera_probe` 报 `depth must be finite and greater than zero: 0.0`。 |
| 已证实根因 | 所请求的彩色中心像素在对齐深度中没有有效值；同一帧仍有约 14.6% 到 18.0% 的有效深度。它是局部深度洞，不是整台相机失败。 |
| 修复 | `camera_probe` 从请求像素向外查找有限且正的深度样本，并在输出中记录实际取样像素和半径。该场景使用 `--depth-sample-radius 50` 成功。 |
| 防复发 | 不把单像素 `0` 深度等同于相机损坏；输出必须区分“请求像素”和“实际有效样本像素”。对反光、黑色、低纹理、遮挡表面预期存在深度洞。 |

## 8. 临时热身代码保留帧，耗尽 RealSense 帧池

| 项目 | 记录 |
| --- | --- |
| 现象 | 热身诊断用列表推导保存约 30 个 `frameset`，在约第 16 帧出现 `Frame didn't arrive within 5000/10000`。 |
| 已证实根因 | 代码持有旧帧对象，RealSense 的有限帧池无法复用；“约第 16 帧”与该机制一致。 |
| 修复 | 热身改为逐帧等待后立即丢弃：`for _ in range(30): pipeline.wait_for_frames()`。 |
| 防复发 | 流式读取不积累 `frameset`、图像或 SDK 句柄；所有 `pipeline.start()` 必须有对应的 `pipeline.stop()`，包括异常路径。 |

## 9. Viewer 的稀疏 3D 图与 Python 取帧失败被混为一谈

| 项目 | 记录 |
| --- | --- |
| 现象 | RGB 图像清楚，Viewer 3D/深度显示有空洞；另有 Python 等待帧超时。 |
| 已证实事实 | 稀疏深度可由目标表面的低纹理、深色、反光、遮挡或无效像素引起；它不自动证明 USB 或相机损坏。 |
| 部分证实的运行问题 | Viewer、旧 Python 进程或旧 dashboard 占用相机时，新进程可能不能获得帧；直接 USB 3.x 和单一采集进程是成功会话的共同条件。 |
| 防复发 | 先在 Viewer 确认设备身份、RGB、Depth 和 USB 3.x，再关闭 Viewer 后只启动一个 Python 采集者。相机深度接受标准是“目标区域存在有限深度与可重复的点”，不是 3D 预览看上去满不满。 |

## 10. 输出文件 `Permission denied` 的根因未被伪造为相机错误

| 项目 | 记录 |
| --- | --- |
| 现象 | 写 `camera-a-final-computer.json` 时出现 `Permission denied`。 |
| 未证实部分 | 当时没有直接证据区分只读属性、被进程占用、目录权限或其他 Windows 锁定原因。 |
| 正确处置 | 将它标为输出路径故障，不把它解释为 RealSense 测量失败；在可写的新文件名/路径上成功保存后继续。 |
| 防复发 | 运行前关闭可能预览 JSON 的程序；为每次采集生成带日期的新输出文件；若复现再检查属性、占用进程和 ACL。 |

## 11. 手工红色圆点和缩放打印破坏了几何标定质量

| 项目 | 记录 |
| --- | --- |
| 现象 | 初期用大小不稳定的手绘红圆作标定点；随后发现打印板的 100 mm 标尺实际仅约 95 mm。 |
| 已证实影响 | 没有固定几何中心和实际尺度的目标不能作为可重复的参考。打印缩放会把纸面所有长度系统性带偏。 |
| 修复 | 改用平放、固定 `10 x 10 mm` 的非反光红方块，使用几何中心定义位置；A4 板只接受 100 mm 标尺实测 `99-101 mm` 的打印件。 |
| 防复发 | 先用尺验证物理基准，再采集像素；不得以“图形看着正确”代替长度检查。 |

## 12. 早期平面映射误差大或姿态漂移，仍曾被误认为接近可用

| 项目 | 记录 |
| --- | --- |
| 现象 | 一份映射的保留点误差为 `28.053 mm`；另一份 v2 记录在恢复后 P0 像素约漂移 `75 px`。四角红方块映射的独立点平均误差为 `3.183 mm`、最大 `4.290 mm`，留一诊断最大达 `11.492 mm`。 |
| 已证实结论 | 这些结果不满足自动定位的证据要求。相机、纸面/P0 几何、人工放置或目标质心中至少有一项不稳定。 |
| 修复 | 淘汰旧 artifact；以机器生成的已知点和独立保留点重测；最终升级为六 ArUco 参考板和质量闸门。 |
| 防复发 | 拟合点永远不能同时充当验收点；报告保留点平均/最大误差；相机、板、纸面或 P0 变化后，旧映射自动失效。 |

## 13. 画面中的错误红色候选曾接近触发错误运动

| 项目 | 记录 |
| --- | --- |
| 现象 | 实时流在纸面红方块与位于约 `(248,44)` 像素的另一个红色部件之间切换；后者投影到 A4 范围外。 |
| 已证实根因 | 早期红色分割只有颜色/形状条件，缺少“候选必须位于参考板定义纸面内”的几何约束。 |
| 修复 | 页面只接受中心投影在注册 A4 区域内的红色候选；纸外候选在发送任何动作前被拒绝。 |
| 防复发 | 目标检测必须同时满足类别、几何工作区、深度/平面和稳定性约束。颜色相似不等于可执行目标。 |

## 14. 自动化测试曾意外打开真实 COM4 并使机构运动

| 项目 | 记录 |
| --- | --- |
| 时间 | 2026-07-29 |
| 现象 | 为连续跟随新分支增加测试时，测试参数带有 `--execute`、`--physical-preflight` 和 `--z-drop-mm 1`，而连续分支尚未先行处理。测试进入既有单目标执行路径，在真实 `COM4` 执行了 `X+2.513`、`X+2.513`、`Z+1.000 mm`。 |
| 已证实根因 | 测试没有注入假控制器，且分支顺序允许真实执行参数到达实串口路径。 |
| 修复 | 测试改为注入 fake controller；连续分支在既有单目标执行逻辑之前处理，并拒绝非零 Z 下落。 |
| 防复发 | 单元测试默认不得拥有真实端口；真机测试使用独立显式命令和现场前提。任何意外真实动作后，立即停止后续命令并人工恢复 P0。 |

这是本项目最严重的软件安全事故，因为它不是操作者显式发起的真机命令。

## 15. 网页服务存活，不代表相机链路仍可用

| 项目 | 记录 |
| --- | --- |
| 时间 | 2026-07-30 |
| 现象 | `http://127.0.0.1:8765/` 可打开，但页面为 `camera_error`，提示 `Device disconnected. Failed to reconnect: No device connected`，没有图像与坐标。 |
| 已证实根因 | 旧 dashboard 进程从前一日持续运行，曾经历相机断连，无法在该会话中恢复。此时 Windows `Get-PnpDevice` 仍显示 D435i RGB 和 Depth 两项均为 `OK`，故不是“相机已从 Windows 消失”。 |
| 修复 | 只停止旧 dashboard，关闭其他相机占用程序后以相同参数启动新进程；新会话恢复 `ready`、六标记可见，保留误差平均 `1.134 mm`、最大 `1.719 mm`。 |
| 防复发 | 页面必须把 `camera_error` 当作不可用状态；相机重插或断连后重启采集会话并等待新的 `ready`，不能只因端口 `8765` 仍在监听就相信视觉数据。 |

## 16. 文档和沟通本身也曾成为失败点

| 项目 | 记录 |
| --- | --- |
| 现象 | 早期 README 的“当前结论”仍写 D435i 尚未接入，而后续已存在显示标定和受监督 XY/Z 演示记录；此外，参考板与相机重装的关系、打印尺寸和坐标方向没有在一开始被说清。 |
| 已证实影响 | 文档状态与真实项目状态不同步会造成重复标定、错误预期和对“是否已完成”的争议。 |
| 修复 | README 已标记早期结论的时间范围，并链接标定、全流程、新电脑和本失败复盘文档。 |
| 防复发 | 每次完成一个真实硬件里程碑或发现一个失败，都新增原始记录和更新索引；报告必须分别写“代码已实现”“离线测试通过”“现场验证通过”“尚未验证”。 |

## 17. 当前未关闭的风险清单

下列事项不是已经修复的失败，仍必须在后续工作中保持可见：

1. `Pn:P` 的硬件根因尚未排查，不能做探针 Z 标定。
2. 当前视觉验证针对纸面内红方块，不是杂草检测或真实目标抓取。
3. 纸面坐标误差通过质量闸门，但尚未建立整个工作区的独立误差地图。
4. P0 仍为人工基准；没有自动回零、编码器闭环和独立急停硬件。
5. Z 只验证过固定 `1 mm` 下落，不具备由深度自动规划高度或接触动作的依据。
6. D435i B 仍需独立设备验证和独立标定，不能复用 A 的 artifact。

## 18. 失败后的统一处置顺序

```text
发现异常
-> 停止后续运动；机械风险时先断 12 V
-> 保存原始错误、状态帧、设备身份和现场观察
-> 区分通信、供电、机械、相机、标定、文件与测试层
-> 只做一个最小可验证修复
-> 先离线/只读验证，再做小范围真机验证
-> 更新原始记录、结论状态和防复发措施
```

事故后最不应做的事是：重复发送运动命令、用旧 MPos 解释物理位置、把暂时恢复的画面当作标定有效，或在没有证据时宣布“已经解决”。
