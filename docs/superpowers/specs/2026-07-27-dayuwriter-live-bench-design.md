# DayuWriter 真实串口现场演示台

## 目标

为非电子专业观众提供一条可核对的因果链：动作按钮 -> Python 持久控制器 -> 实际串口 TX -> GRBL RX -> 状态轮询 -> Idle 完成。界面不得制造运动、时间戳或串口事件；所有通信内容必须来自现有 `TraceEvent`。

## 设计方向

采用明亮、分区清晰的通信课堂风格。顶栏显示当前端口、连接状态、GRBL 状态和 `MPos`；中央通信流水逐条显示真实事件，并同时给出通俗解释和技术含义；右侧显示 XY 坐标平面、Z 坐标和 P0 注意事项；左侧保留受限的真实微动和只读状态查询。蓝色用于 Python，橙色用于 TX，绿色用于 RX，紫色用于坐标，红色只用于错误。

每条事件都更新“当前结论”区和 Python/协议代码区。说明分成两层：先用一句日常语言告诉老师这一步发生了什么，再用协议术语解释为什么；坐标区只画 GRBL 返回的 `MPos`，不会把像素坐标或相机坐标冒充成机器坐标。

## 因果链语义

| 真实事件 | 节点 | 对观众的说明 |
| --- | --- | --- |
| `CALL` | Python 调用 | Python 正在调用持久控制器 |
| `TX`，内容不是 `?` | TX 运动指令 | Python 已把运动指令写入串口 |
| `RX ok` | RX ok | GRBL 已接收指令；这不等于运动完成 |
| `TX ?` | TX ? | Python 正在询问 GRBL 当前状态 |
| `RX <Jog...>` 等非 `Idle` 状态 | RX Jog | GRBL 报告运动仍在进行 |
| `RX <Idle...>` | RX Idle | GRBL 报告 Idle，控制周期已完成 |

非 `Idle` 状态会显示为运动中，`error`/`ALARM` 仍由控制器原有错误路径处理。`ok` 不被解释为物理运动完成。

## 非目标与安全边界

- 不改变 `GrblWorker`、`GrblController` 或 P0 XY 边界。
- 启动窗口不自动打开 COM 端口；用户点击连接后才执行首次只读状态查询。
- 不加入任意 G-code、自动寻零、设置写入或视觉联动。
- `MPos` 仍是 GRBL 报告的位置，不是编码器测得的绝对物理位置。
- 不显示伪造时间戳；事件编号只表示本次窗口收到的顺序。

## 验证

- 纯函数测试验证每类真实事件映射到正确的节点和中文解释。
- 运行 `tests/dayuwriter` 全套离线测试。
- 使用 Windows 窗口截图检查首屏文本、按钮和日志区布局；不连接硬件进行视觉布局检查。
